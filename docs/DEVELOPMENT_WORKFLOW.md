# Synlen 开发流程

> 本文件管「走的流程」；`DEVELOPMENT_STANDARDS.md` 管「写出来的样貌」。
> 配套：`AGENTS.md`（入口）、`CONTEXT.md` + `docs/adr/`（领域语言与决策）、`.agents/skills/`（各环节技能）。

## 1. 按规模适配

| 规模 | 例子 | 走的步骤 |
|---|---|---|
| 小改动 | 修一个 bug、改一个文案、调一个参数 | §4 实现 → §5 提交 |
| 中功能 | 新增一个页面 / 能力 | §2 定规格 → §4 → §5 |
| 大功能 / 重构 | 阅读器引擎改造、新增整个模块 | §2 → §3 拆票 → §4 → §5 评审 → §6 |

判断标准：涉及**跨层架构**、**超过 3 个文件**或**影响数据模型**时，至少先定规格。

## 2. 定规格

- 值得做的工作先建 issue（`gh issue create`），正文即规格：背景、验收标准、技术路径。
- 新术语或概念冲突 → 落定 `CONTEXT.md` 的规范词。
- 同时满足难逆转 / 无上下文会困惑 / 真实权衡 → 写 `docs/adr/NNNN-*.md`。
- 拿不准的交互先做可抛弃原型，再进正式实现。

## 3. 拆票

- 规格拆成可独立完成、边界清晰的 ticket（GitHub issue），每个声明阻塞关系与上下文。
- 标注优先级与归属（人工 / Agent）。

## 4. 实现

- 新功能与核心逻辑必须带测试；复杂逻辑用红-绿-重构的测试驱动方式推进。
- 新模块按深模块原则设计：小接口 + 大实现（规范 §3）。
- 重构与功能分开提交；重构走 ADR-0001 增量纪律（路过即修，不做 big-bang）。

## 5. 评审与提交

- 改动用 `syn-code-review` 过一遍：标准轴（分层 / Riverpod / 六项阻断）+ 是否贴合原规格；不通过就回 §4 修复后重评。
- 提交前：`flutter analyze` 零告警 + `dart format` + 按 `syn-pre-push-checks` 选的最小测试证据。
- 提交信息 `type(scope): 中文描述`；一个逻辑一个 commit。
- 推送 / 合并前：全量 `flutter test` 必须全绿。

## 6. 维护

| 场景 | 动作 / 技能 |
|---|---|
| 用户报 bug | 建 issue，标注优先级 |
| 疑难 bug / 性能回归 | 先定位根因再动手修 |
| 简化机会 | `syn-find-simplifications` → Agent Note 提案 |
| 文档结构与审计 | `syn-doc-standards` |
| 文字精简与审查 | `syn-prose-standard` |
| 会话视角泄漏清理 | `syn-trim-cot-leakage` |

## 7. 硬性底线（所有改动都受约束）

1. **实现前必须有 ticket**（哪怕只有一句话的 issue），杜绝无主开发。
2. **提交前必过**：`flutter analyze`（零 error 零 warning）+ `dart format` + 最小测试证据；推送 / 合并前全量 `flutter test` 必须全绿。
3. **新功能 / 核心逻辑必须带测试**；测试不过不合并。
4. **重构与功能分开提交**；重构走 ADR-0001 增量纪律。
5. **注释与文档用中文**；标识符、命令、标签保持英文（规范 §8.1）。
