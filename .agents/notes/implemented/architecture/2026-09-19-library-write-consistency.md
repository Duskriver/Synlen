# Agent Note: 导入、恢复与删除共用藏书事务

Status: implemented

## Problem

导入的书目与清单双写已有事务，恢复却逐表合并，第二步失败可能留下部分更新。删除通过手工补偿重建数据库记录，但先删掉的文件无法随数据库补偿恢复。导入失败还可能删除操作开始前已经存在的文件。旧 EPUB 导入测试只调用预设 mock，没有执行导入流水线，不能约束这些结果。

## Decision

`LibraryBookStore` 拥有书目与清单的跨表写入：导入双写、恢复时在同一事务内读取本机值并合并双写、删除时原子写入墓碑并移除清单。恢复的元数据与进度比较规则由 `backup_merger.dart` 的纯函数承担，保留秒精度清单比较、较新阅读进度和显式恢复撤销软删除的语义。

`BookFileChanges` 为单本导入或恢复建立文件补偿作用域。写入已有文件前保存副本，替换内容先在同级临时文件完整写入，避免被跳过的封面写入失败破坏原件；数据库事务成功后提交文件作用域，失败则恢复原件并删除本次新建文件。补偿副本放在目标文件的同级临时目录；补偿失败保留副本并报告失败，避免删除唯一原件。

`BookDeletion` 在 application 先提交逻辑删除，再清理文件。事务失败不触碰文件；清理失败返回 `cleanupPending` 并记日志，书架仍按已删除处理，残留文件可由存储清理重试。文件系统不参与 SQLite 事务，已提交的墓碑不会因清理失败撤销。

## Alternatives considered

**保留删除的逐步补偿**：恢复数据库记录无法恢复已删除的原书或封面，会使书架状态宣称文件仍可用。

**为所有文件操作建立持久化事务日志**：本次需要的是运行中失败的补偿与幂等清理。跨进程崩溃恢复还涉及日志版本、启动重放和迁移，不能由临时副本假装保证。

**只增加 mock 调用断言**：无法证明数据库回滚或文件保留。测试运行真实 ZIP、临时目录和内存 SQLite，在真实写入处用触发器注入失败。

## Consequences

- 恢复按单本书原子提交；后一本失败保留已成功恢复的书及成功数。
- 删除提交后即为逻辑成功；清理失败保留墓碑和待清理文件，后续重试不重建书目。
- 文件补偿覆盖运行中异常，不保证进程被杀时跨数据库和文件系统的原子性。数据库孤儿修复与物理文件清理仍各自承担恢复职责。
- 测试覆盖第二张表失败、旧元数据与封面恢复、新文件清理、重复导入、墓碑保留、删除事务失败和清理重试。
