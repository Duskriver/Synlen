# Agent Note: 默认本地发布，云构建作为手动备用

Status: implemented

## Problem

每次 tag 发版都从新的云端环境准备 Android 构建，等待时间影响小版本修复。v0.3.2 的云端发布用时约 15 分钟，其中 APK 编译 7 分 36 秒；本机一次正式签名构建用时 165.8 秒。本地已有可复用的依赖与编译缓存，但手动拼接检查、双平台上传和清单更新容易漏步，也容易在上传失败后重建同一版本造成摘要变化。

## Decision

`tool/release.sh` 是本地与手动云构建的共同入口，先执行格式、分析、Flutter 全量测试、分层、Rust、文档和 reader Web 门禁，再构建并校验正式签名 ARM64 APK。源码与版本说明必须提交；推送和上传都在检查之后。

APK 验证读取安装包内部的包名、版本号、构建号与 ABI，检查 [16 KB 对齐](../bug-fix/2026-09-19-android-native-page-alignment.md)，并通过 `apksigner` 验证签名及已发布证书摘要。产物旁的 JSON 记录源码提交与 SHA-256；`--apk` 只复用记录匹配的原文件，重试仍执行质量门禁。

默认命令推送 `main` 与 tag、同步 Gitee、上传并验证 GitHub APK，再调用现有 Gitee 上传脚本更新客户端清单。`--prepare-only` 只产出经过验证的本地文件。GitHub tag 推送不触发构建；手动工作流检出指定 tag，执行同一命令，并在发布失败时保存产物供重试。

本决策部分取代 [Gitee 分发决策](2026-09-17-release-distribution-via-gitee.md)的构建触发方式；其分发协议与凭据约束仍有效。[发版门禁超集](2026-09-09-release-gates-superset-of-pr.md)继续约束两种执行环境。操作步骤由[发布手册](../../../../docs/cookbook/publishing-a-release.md)持有。

## Alternatives considered

**继续以云端自动构建为默认，仅修缓存与并行化**：能缩短耗时，但日常发布仍需要云端初始化和网络等待；单人维护已有可用的本地签名环境，直接复用更合适。

**只手动执行构建与上传命令**：步骤缺少统一门禁与版本、签名校验，上传失败后也无法确认重试文件是否仍来自同一提交。

**本地和云端分别维护发布步骤**：检查与版本规则容易漂移。两边只在环境准备方式上不同，执行同一脚本即可共享约束。

## Consequences

- 本机持续复用缓存，代价是发布依赖本机 SDK、签名密钥与网络；云端保留可替代执行环境，不能承诺每次本地构建耗时相同。
- 本地进程锁与云任务检查减少重复发布，跨电脑同时启动仍由发布者避免；Gitee 文件 SHA 条件写入与同版本摘要约束继续作为最终保护。
- 脚本测试使用临时 Git 仓库与外部命令替身，覆盖演练、失败阻断、tag 冲突、签名及元数据错误、源码与产物变化、双平台同文件发布和上传失败后的重试；APK 校验另外使用真实正式签名包验证。
- Gradle 替身校验完整的 Readium 与 OTA 测试任务列表，参数不符时显式退出；仅依赖 `set -e` 处理独立的 `[[ ... ]]` 断言，会因 Bash 版本差异漏报失败。
